# 0027 - 统一通道 + routeSession：IM 单窗口接入的会话模型与上下文交接

日期：2026-08-18（routeSession 设计讨论重建，源自本会话转录若干轮 /grill-with-docs）

## 状态

讨论中（design 未定稿；用户最后提出 HANDOFF 方案，助手反方评审未完，等待用户裁决）

## 背景

多通道（IM/App/Web）立项需要投递层（ADR-0026 P2）支撑。IM 通道有**单窗口软件形态约束**：系统与用户固定一个聊天窗口。如何让 IM 通道在约束下接入一个天然多会话（Web/App 可多标签页、多 session 并发）的产品，是本 ADR 的核心问题。

用户核心立场（决定一切设计的北星）：
> 「我们的项目核心是产出，产出的质量是系统质量最关键的标准。如何保证产出的质量，LLM的上下文是关键。」

本 ADR 记录 routeSession 的迭代设计史：方案提出 → 用户裁决（接受/拒绝/条件接受）→ 反例 → 收敛。

## 一、方案提出节点

以下每次方案（含被否、被采纳、被部分采纳者）均取自转录原文摘要。

### S1. 双游标模型（助手早期，否）
「Web=客户端持游标、IM=服务端持游标」的通道分线。
用户否决原话：
> 「双游标模型完全没有必要，如果IM支持服务端游标，那么Web/APP肯定也能支持！」
> 「真正的问题是Web/App可以有多个session，但是IM 只有一个（软件形态就是有这个限制）！！！"
**拒绝理由暴露**：Web/IM 分线是**假维度**，真正的维度是「消费者是哪个 session」——Web 多 session 是真并发消费者，IM 单窗口是单消费者；游标模型应统一为「每消费者一行」，而非按通道类型分两套。

### S2. routeSession 初版（用户 6563/6567 提出）
> 不对，我觉得更好的设计是在IM channel 这种单session的通道里和Web/App所有的session之上建一层routeSession。session里的run/cron system通知和游标 逻辑转发到routeSession， routeSession 作为IM 的 唯一session！
> 用户所有的文本在routeSession里通过LLM 路由到 内容正确对应的session里。

**助手初理解（6569）**：routeSession = 一等公民会话（有自己的 event log + pi session 做路由 LLM）。IM 不是 N 个会话的消费者，只消费 routeSession 一个会话——「游标一行，天然满足 IM 单通道」。某会话的通知事件镜像进 routeSession 的 log（带 sourceConversationId）。助手确认后遗留两点待定：转发哪些事件（倾向只转发通知类事实）、routeSession 实体放 P2 还是 P3（倾向投递层接缝 P2、路由实体 P3）。

### S3. 用户完整需求（grill-with-docs 参数，6580/6589）
> routeSession 与用户一一绑定，每个用户唯一！使用默认公司ws，用户的普通session作为历史真相源，routeSession 可以有switchSession，切换当前ws，到用户有权利访问的[其他]ws。但是需要通过用户的意图分析后，按意图或要求切换，以保证写入不会乱目录！这个用户最近7天的所有定时任务或后台任务以表格形式注入prompt，最近3天的活跃session 提取记忆摘要，也注入prompt，让routeSession可以全局了解情况！找不到对应记忆，可以按历史顺序倒查更久的历史记忆摘要。对应上了，就可以route切换到对应session（逻辑切换，routeSession 程序性转发）。长时间对话暂停，或用户消息和历史对不上，就会重新匹配一次session。

### S4. grill 设计树第一轮 Q1–Q8（助手 6703）
八问覆盖：routeSession 实体形态（conversations 一行 vs 新表）、转发力学（同步嵌套 vs 异步镜像+零转述）、switchSession 作用域（改自己 cwd vs 只改路由候选集）、记忆摘要子系统（session_summaries 新表，惰性生成）、当前目标状态（currentTarget+lastActiveAt）、switch 与 route 是否一机制、分期、职权边界（是否永不直接起 run 写文件）。

### S5. 用户三答（6713）
> Q1 我觉得routeSession 纯逻辑层，因为和用户一对一强绑定，所以不需要数据库的毒[独]存一行，在代码里以session的子类拓展逻辑即可！
> Q2 (b)，但是仍然需要考虑，当话题出现转换时，如何判断是否需要切换 SESSION ！每一次都独立调用一次LLM，token和时间都有浪费。这是最稳妥的方案。我们可以考虑一下有没有其他更优秀的方式
> Q3 我在想这种转发实在复杂，更合理的设计是改变这个session的history和memory 设计！由于IM特殊性质，系统与用户固定一个聊天窗口，理论上就一个session。我们可否按时间来切换session？但是用户时间也不能作为确定性依据！！

### S6. 单会话 + 聚合记忆 + 定向执行（助手 6720，回应 Q1/Q2/Q3）
三个否定（不存 DB 行、不做每消息路由调用、不按时间切换）指向一个收敛：**routeSession 永远唯一，话题接续靠记忆聚合注入，执行定向靠工具直接引用 runId/questionId**——转发/切换/状态全死。L2 记忆层被改造：全局聚合注入（7 天任务表 + 活跃会话摘要 + 挂起 run + 待处理卡）。补丁：加 `read_conversation` 工具按需拉深层细节。承认真实代价：跨窗口深聊细节有损、注入预算、单窗口抢子。

### S7. 方案 A vs 方案 B（助手 6735，回应「IM 聊天怎么注入历史」）
- 不遗失根基 = 「到达即落库」，与 web POST /messages 全同构（appendMessage → 事件日志同事务 → pi turn），IM 平台侧弱点碰不到服务端。
- A（不并，推荐）：IM 聊天只活在 routeSession 自身线性历史；普通会话只装领域动作真相（run/brief/卡/文件）。
- B（投影）：消息同时追加归档投影进目标会话（不触 turn）。
- 关键洞察：路由判定不是独立 LLM 调用，是**回复的结构化副产出**（targetConversationId 字段），零额外 token。

### S8. 模型乙：结论外化 AGENTS.md（助手 6749，回应「第二天回 S 对结论异议」反例）
「讨论一半」是过程（属于 transcript），「最终结论」是关键决策，born to live outside any conversation。载体 = ADR-0009 记忆层 L2 的 AGENTS.md 关键决策节。IM 每轮回复结构化副产出带 `memorize: { wsId, conclusion }` 字段，服务端合并进对应 ws 的 AGENTS.md。零双写、零消息复制。
**同时抛出分歧**：模型甲（真·路由归属，IM 文本落进归属会话 S、S 起 turn）与模型乙（讨论留 routeSession + 结论外化）对立。

### S9. 单点真相收敛（助手 6762，回应「5 次交叉」反例）
5 次交叉场景证明「分散 + 事后外化」全死——AGENTS.md 只救结论不救过程、read 摘要有损、双向镜像双写债。结构性原因：**讨论被存进两个互相不知道对方的格子**。收敛：
> 普通会话（讨论）= 唯一真相。IM 不是另一个会话，IM 是「当前讨论的入口 + 视图」。routeSession 不持有自己的消息历史——它只持有一个会话级状态：当前活跃讨论。

routeSession 回到用户 Q1 的「纯逻辑层、无 DB 行、无自身历史」。残余问题：IM 窗口显示层（永远显示当前讨论 vs 聚合多讨论流）。

### S10. 无指针方案（助手 6775，回应「指针复杂」）
用户认可 S9 后质疑指针仍是复杂设计（"项目后期往往可能会导致灾难"）。助手杀掉「当前活跃讨论」可变状态，改为**每消息结构化副产出判定归属**——targetConversationId 是回复必然副产物，零额外调用、零状态。用表格论证无状态在连续/切换/重启/多入口四情况都**不劣于**指针。

### S11. 无状态被硬否 + 上下文交接（助手 6788）
用户 6780 强硬反对 S10。助手承认根本错误：把「消除状态」当目标，丢了系统真实目标「产出质量」；无状态让每条消息从"摘要重建上下文"起步而非站在连续上下文线上——上下文切碎，对产出是灾难。助手**收回无状态方案**。
新模型**上下文交接（context handoff）**：
- routeSession = 一条真正的流（有自己的 transcript，IM 讨论无损累积）——容器内连续，无需指针。
- 普通会话 = 各自流。
- 跨入口接续 = 一次显式交接：**完整 read 目标会话相关 transcript 并入自己上下文**（完整搬运，不是摘要），判定只在跨界瞬间一次。
5 次交叉重跑全部无损。对比表：指针（连续但靠状态）vs 无状态（每条重建，灾难）vs 上下文交接（容器内连续 + 跨界完整搬运，无状态无指针，判定仅跨界一次，产出质量好）。

### S12. 用户认可 + HANDOFF 数组方案（用户 6797/6801/6803）
> 嗯 这个方案确实更好！但是如果在[IM]话题里突然插入其他话题呢？
> routeSession 注入 最近7天的所有活跃session summary（短小简洁，系统任务定时增量提取，只做增量）， 根据用户对话内容，查询SESSION  SUMMARY，提取 HANDOFF。handoff 在 routeSession 里设置数组，同时最多3个？用户插入话题，就重复执行这一机制。
用户要求助手从**反方角度**推理找问题，并已自己想到一个：
> 我已经想到了一个问题，读取多个 HANDOFF， 交接 IM 回普通session，会出现session之间的内容交叉污染。

### S13. 反方阵列（助手 6809）
对 HANDOFF 方案的六点反方评级：
1. **Summary 累积误差**：增量摘要是对上一次摘要做增量（自引用），误差单调累积且无对账回路；摘要由系统任务 LLM 生成，永远没有真相侧校对——「不断退化的副本」当交接依据。
2. **「7 天活跃」是新状态源**：活跃判定/时效/滚动窗口是状态逻辑，踩死「指针状态」同一个坑；定时增量有延迟窗口，跨界发生在窗口内拿到的过期索引。
3. **数组「最多 3 个」是隐式状态管理**：3 个 slot 满了踢谁？优先级/替换/淘汰全是状态判定；每轮保活判定=判定回潮。
4. **交叉污染的本质不是数量是边界**：2 个 handoff 也会污染，并存才是病根，「限制 3 个」治不了病。
5. **与单真相源收敛自相矛盾**：IM 增量落哪？留 routeSession 则 S transcript 缺段，5 次交叉原地复活；POST 回 S 则引 6。
6. **写入不对称=污染第二张脸**：routeSession 在 handoff 上下文里写的片段 POST 回 S 后，缺生成上下文，S 在错误假设上继续——从并行污染变时序污染。

**改进方向（不推翻用户直觉）**：
1. 摘要降级为「目录」不做「内容」——注入浓缩索引（最近在聊什么、哪个 ws），handoff 内容 = 按索引命中的目标 session **真实 transcript 原文片段**（目录指路不背书）。
2. 每次交接落回目标 session 且带 **provenance**（本段基于哪几个片段的摘要引用），write-back 对称，时序污染消失。
3. 数组降级为「**单 active + 轮换**」——routeSession 任意时刻只有一个激活话题载体，handoff 数组只是候选池索引；上下文物理窗口只有一个话题内容。

## 三、拒绝理由应剥离的设计缺陷/需求

1. **伪维度**：通道类型不是建模维度；消费者（session）才是。IM 单窗口 = 唯一消费者，这是软件形态约束，不是"IM 特殊"——它同样可用服务端游标，却必须是单游标。
2. **指针状态是后期灾难源**：切换逻辑、失效判定、超时重匹配、多入口竞态——每项都是项目后期复杂度。
3. **无状态是产出灾难**：上下文是产出质量的命脉；从摘要重建 = 请"每次都只看一页简报的顾问在同一件事上出主意"。这是**对上下文连续性失焦的最严重拒绝**。
4. **按时间切换不可靠**：用户时间不是确定性依据——不要用时间来承担"该接着哪个话题"的判断。
5. **摘要自引用累积误差**：定时增量提取只做增量 → 误差单调累积、无校验、无真相对账。
6. **多话题并存污染**：不是数量问题（3 个、2 个都污染），是"多个话题共用同一 LLM 上下文物理窗口"的结构问题。

## 四、反例场景（保真，不压缩）

**R1 跨入口结论丢失**：
> 那么普通Session里，一个问题我们讨论了一半。接下来我们是否可以在IM里面继续讨论，并且得出最终结论？第二天，又回到普通的 SESSION，我说对最终结论有一些异议。这个时候普通的 SESSION就完全获取不到我们在IM里面讨论得到的结论！

**R2 五次交叉讨论**：
> 这里的情况，如果变成一个问题分了五次讨论，且交叉分布在普通 SESSION和 IM 里呢？那么这样子整个讨论都无法继续，无法完成

**R3 话题突然插入**：
> 如果用户在话题里突然插入其他话题呢？

**R4 交叉污染（用户自己发现）**：
> 读取多个 HANDOFF，交接 IM 回普通session，会出现session之间的内容交叉污染。

## 五、收敛结论（逐轮）

1. **投递层**：per-conversation 事件日志 + 每消费者一行游标 + at-least-once + 幂等（按 questionId/messageId）。游标的目的是保证审批/关键操作「发起-应答一一对应」，应答不被忽略也不被重复响应（ADR-0026 决策 4）。多通道统一为单一日志 + 消费者游标，无按通道分线。
2. **routeSession 语义**：纯逻辑层（无 DB 独存行、无自身历史），每用户唯一，绑默认公司 ws；普通会话是历史真相源；IM 是当前讨论的入口/视图。
3. **单真相载体**：讨论必须住在单一会话转录；跨入口接续搬运**完整上下文**（不是摘要）；容器内连续不需要指针。
4. **产出质量 = LLM 上下文质量**：任何牺牲上下文连续性的方案（哪怕省 token/延迟）都是灾难——系统北星。
5. **指针对比**：指针（连续但靠状态）→ 无状态（每条重建，灾难）→ 上下文交接（容器内连续 + 跨界完整搬运，无指针状态）。用户认可上下文交接。
6. **HANDOFF 方案评审中**：助手反方裁决 = 摘要降级为目录、交接带原文 + provenance、数组降级为单 active + 轮换；待用户裁决是否接受「单 active 串行」取代「3 话题并行」——开放问题：**"并行跟踪 3 个话题"是否真实需要**（IM 用户天然串行）。
