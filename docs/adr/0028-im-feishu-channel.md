# 0028 - 飞书通道 v1：长连接手搓 protobuf + 交互卡片出站 + 三条 #49 决策反转

日期：2026-08-18（spec #55；/grill-with-docs 决策收敛）

## 状态

已接受

## 背景

IM v1 平台无关基础设施（#49）已留好「平台适配器」下游口子，现接第一个真实平台：飞书（应用机器人，企业自建应用，全员可用）。设计对抗确认三项 #49 决策在飞书场景需反转，并锁定 transport 实现策略。核心事实（官方取证）：飞书长连接**每应用一条连接服务全租户**（非 per-user，集群模式随机单 client），出站是 REST 短连——多用户无连接数性能障碍，瓶颈在飞书 API 限频。

## 决策

1. **approval/task 重开 IM 端——但只开「卡片按钮」**（重开 #49 决策 5）：飞书**交互卡片按钮**是确定性通道（点击回调带身份、非文本、on-the-record）→ 审批/任务卡可在 IM 上直接批/拒/确认，走既有 dispatch + CAS。「确定性动作只在确定性通道」的 ADR-0022 口径不变——**文本仍不放行** approval/task（命中→提示去 Web/App）。新的回执文案区分真伪（不存在假装成功）。

2. **绑定转向用户自助**（推翻 #49 决策 6）：已登录 Web 用户生成 **10 分钟有效、单次使用** 的绑定码，到 IM 发 `#bind <code>` → 该 IM 身份（open_id）绑到本人账号；`#unbind` 自助解绑；admin 降级为**只读列表 + 兜底解绑**（离职等场景），不再静态新增绑定。原因：静态 admin 绑定面对「全员可用」不可运维（admin 无法预知全员 open_id）；「Web 发码 + IM 输码」是双向认证，码泄露被 TTL/单次消费收敛。绑定成功瞬间对存量 pending 卡**补发一次**（用户最该看见历史积压的时刻）；不做启动扫描补发（防重启风暴）。

3. **入站文本语义反转**（改 #49「文本只答最新 pending」→ 全扫描 + 选择卡）：文本回流扫**全部可应答（kind=ask）pending 卡**：0 张→丢弃（有 approval/task 则提示去 Web）；1 张→直接归一化判答；**>1 张→发「选择卡」**列出各卡（仅 prompt）问清目标，服务器缓存那句待确认文本（TTL 10min、新输入覆盖），点击后套用判答。原因：多张 pending 并存时「最新」猜不准用户意图；选择卡把歧义显式化。

4. **transport 手搓 raw protobuf 长连接（Bun）**，官方 Node SDK 弃用：实证官方 Node SDK 在 Bun 有**静默丢事件**风险（larksuite/node-sdk issue #201：Bun 1.3.x 长连接负载下静默丢；另有 #186/#164/#177 重连/泄漏）——「事件不丢」是 IM 通道核心承诺，静默丢失不可接受。手搓基于 MIT 开源的 pbbp2 帧协议（Python/Rust 社区有可运行重实现佐证路径可行）；**stub 假服务器与生产 client 共用同一 protocol codec**（stub 即飞书侧的另一半）→ 协议在 CI 内可全量测试；真飞书 live 作最终验收（凭证 env 注入，按钮点击走手动清单）。

## 后果

- 与 #49 的语义差异以本 ADR 为权威；#49 相关测试按新语义修订（挂 spec #55 的 T 系列）。
- 交互卡片回调（`card.action.trigger`）走同一长连接、3s 内同步响应；收尾用「更新卡 + toast」，不做 PATCH 卡更新（14 天窗/仅 interactive，成本不值 v1）。
- 出站 `uuid = ${questionId}:${frame.type}` 幂等键防重试双发；「响应只处理一次」仍由域表 CAS 保证（与 #49 决策 4 一致）。
- 卡片底部「都不满意？直接回复想法」提示按 resumeSchema 开放度显隐（闭合 enum 不提示）。
- 钉钉同 seam 后续接入（本 spec 出范围，第二批）。
