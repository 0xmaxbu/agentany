# 管理模块 v1：实体范围与领域定义

chat 主链（slice②）真验收通过后，启动「用户/项目/系统/工作流/Skill/定时任务」6 实体的管理功能。grill（领域建模）第一轮定了产物形态与两个新领域词的含义。

## 决策

1. **形态**：后端 CRUD（数据模型 + API）与管理面 UI 两者都要，**v1 先后端**——数据模型与鉴权边界不可逆性高，先钉死；UI 迭代成本低，后做。
2. **「系统」= 实体**：系统是承载全局、跨项目配置（安全姿态 `SECURITY_POSTURE`、运行参数、全局开关等）的**实体**，对所有项目/会话生效。
3. **「定时任务」= 用户可配 cron 触发工作流**：定时任务是用户配置的 cron 触发器，到点自动启动指定工作流，归属项目。
4. **v1 范围 = 用户 + 项目**：v1 聚焦用户与项目管理（真 auth + 多租户成员关系的地基）。系统 / 工作流 / Skill / 定时任务为后续阶段（见下）。

## v1 范围与后续阶段

| 阶段 | 实体 | 原因 |
|------|------|------|
| **v1（先做）** | 用户、项目 | 真 auth、多用户、项目成员可见性的地基；现 greenfield（无表）必建 |
| 后续 | 定时任务（用户 cron） | Q3 定的大功能：cron 引擎 + 归属 + 权限 + 成本 + 重试，独立立项 |
| 后续 | 系统（全局设置） | 全局配置管理面（admin），中等复杂度 |
| 后续 | 工作流管理 | 现纯 coded 静态注册，改代码即变，管理面价值低 |
| 后续 | Skill 管理 | 现文件自动发现（ADR-0005），进/出靠 `skills/` 目录，管理面价值低 |

## 考虑过的备选（未采）

- **系统**：当作「范围限定词」（系统级 vs 项目级，复用 #10 的 general scope）而非实体。未采——独立实体更贴合「系统设置」的管理语义。
- **定时任务**：「内部系统调度」（经验提取/清理/备份，接 ADR-0008 的 `extractLearnings` 桩）。未采——优先做面向用户的产品自动化能力；内部调度后续独立处理。

## 后果

- 定时任务（用户 cron）是**大功能**：需 cron 引擎 + 触发器归属（项目级）+ 权限（谁能建）+ 执行成本（谁付 token）+ 失败重试。逐项在后续 grill 钉。
- 系统实体引入全局配置管理面（admin 性质）。
